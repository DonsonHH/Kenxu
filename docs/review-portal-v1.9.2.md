# Kenxu 1.9.2 — HTTPS 中转入口与分类采集修复

## 问题与变更

普通页面已有 HTTP → HTTPS 固定源跳转，并保留安全 Cookie、HSTS 和敏感请求拒绝机制。但 WebSocket 的 `upgrade` 事件不经过 Express 中间件，中转桥缺少同样的协议检查。隔离测试复现了来自受信任 Tunnel 的明文握手被接受。现在页面与中转桥共用受信任回环协议判定；中转桥在连接后端之前拒绝公开 HTTP 握手，安全握手与私有回环探针保持可用。只调整 Kenxu，不修改其他子域名或 Cloudflare 全域设置。

复核还发现一台共享核心的原生总量继续上报，但分类记录排队超过一天。队首批次顺序连续、身份与字节有效，目标 DNS 标签包含下划线，被网页主机名式校验拒绝，导致后续分类批次无法按序提交。接收端现允许 DNS 服务／缓存标签中的下划线，并在 ASCII 规范化之前拒绝原始空白和控制字符，继续拒绝 URL、无效标签、超长字段和无效来源。

## 计量与兼容边界

- 原生用户累计字节仍是总账；分类批次不会再加到账单或额度中。
- 不改变节点、负载均衡、账号授权、个人凭据、订阅源或分流规则。
- 原有队列保留并按序重传；重传沿用原序号、时间、字节与幂等指纹，不估算缺失流量。
- 登录、配置和 Bearer 请求通过明文入口时继续拒绝，不重放到 HTTPS。
- 用户端公开访问使用 HTTPS；Tunnel 到同机回环以及 SSH 内的私有管理连接无需改造成另一个公网入口。

## 验证

两条回归均先在原实现上失败，再在修复后通过：明文 WebSocket 握手不得连接后端；带下划线的真实形状分类批次可接受、按序处理和幂等重试，且原生总账不变。保留 URL／控制字符、错误身份、顺序间隙、重复冲突和跨用户访问的拒绝测试。

发布前验证当前代码的完整单元／接口套件，发布后重新检查 HTTPS 跳转、公开与私有健康接口、分类队列、当前配置同步以及实际订阅。现场结果和 GitHub／发布文件清单保存在工作区的私有复核目录，不把真实目标、来源 IP、订阅链接或凭据写入本仓库。

上一轮采集器修复在部署仓库中独立维护；Windows 跳过的 POSIX 检查不替代 Linux 验收。历史校准结果也不代表本次所有历史分类可恢复。
